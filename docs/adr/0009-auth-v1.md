# 0009. Auth v1: actors, API tokens and cookie sessions

- **Status:** Accepted
- **Date:** 2026-09-26

## Context

v1 must attribute every change to a human or an agent, let agents authenticate non-interactively, and let people use the web UI. Full identity management (passwords, SSO) is not needed while the tracker is in development.

## Decision

- **Users.** Users have `kind` = `human`, `agent` or `system`, and `role` = `admin` or `member`. Agents are ordinary users, so history reads "claude moved ENG-4".
- **API tokens.**
  - Format: `trk_` followed by 40 base62 characters, generated with rejection sampling.
  - Storage: only a sha256 hash plus a display prefix. A token is high-entropy, so a slow hash adds nothing.
  - Lifecycle: tokens can expire and be revoked. `last_used_at` is refreshed at most once a minute.
- **Web sessions.**
  - The cookie is `tracker_session`: HttpOnly, `SameSite=Lax`, and `Secure` under https or when configured.
  - The server stores only its sha256 as the session id.
  - It is obtained by pasting a token (`/auth/token-login`), or through `/auth/dev-login` when `TRACKER_AUTH_MODE=dev`. That mode is refused when `NODE_ENV=production`.
  - `EventSource` sends cookies but not headers, which is why the web UI uses sessions rather than tokens.
- **CSRF.** Cookie-authenticated unsafe methods must be same-origin, checked through `Origin`, then `Sec-Fetch-Site`, then `Referer`. Bearer requests are exempt.

## Consequences

- A real login (e.g. better-auth with email/OAuth) can be added later by issuing the same sessions. Tokens and actors don't change.
- There is no per-project permission model yet. Every member can act on every project. _(Superseded by [ADR 0021](0021-project-visibility-and-roles.md).)_
